Zero Trust in under a minute

Veo 3.1 Gemini TTS FFmpeg Node.js

Written and produced so there is a piece of technical enablement content that can be watched end to end rather than described. Original script, a shot written against each line, synthetic narration, generated footage, and the cut. Forty eight seconds, seven shots.

Watch on YouTube 48 seconds
script → shot list → narration (TTS) → generated footage → cut

The script

#NarrationShot
01Maria works from home. Her laptop has been signed in to the company network since Monday morning.Maria at a kitchen table, morning light
02On Thursday she signs in to what looks exactly like the company portal. It is not.Over her shoulder, a login form, screen out of focus
03Minutes later, someone else is using her session. In the old model that is already enough.A hooded figure at a desk at night, seen from behind
04Inside the perimeter everything trusts everything. One stolen login reaches the file server and the database.The same figure walking an office corridor where every door opens by itself
05Zero Trust starts from the opposite assumption. No user, no device, no network is trusted by default.A security analyst turning to camera in an operations centre
06Every request is checked on its own. Least privilege, for the shortest time that still works.A badge at a reader, one door unlocks, the others stay shut
07So the next door does not open. The breach stops at one laptop instead of the whole company.The figure stopped at a glass door with a red light on the reader

My part

  • Chose the topic and the angle, and wrote every line of narration
  • Wrote the prompt for each of the seven shots
  • Capped each line at 18 words, because the model returns a fixed 8 second take and a longer line forces a visible loop
  • Built the pipeline, resumable per shot so a failed take is not paid for twice
  • Reviewed every take and reshot the one that did not fit

The AI's part

  • Voiced the narration I wrote
  • Generated the seven takes from my shot prompts
  • Chose nothing about what the video says, and nothing about which takes made the cut

What I decided, and what I checked before publishing

  • No text on screen. A caption that repeats the narration makes the viewer read and listen to the same sentence at once, and they lose the sentence.
  • No generated presenter. Lip sync that drifts inside an eight second take is the single thing that makes AI video read as cheap, so narration over footage instead.
  • Continuity written into the shot list, not left to the model. Text to video has no memory between takes, so the intruder is always shot from behind and the recurring character carries the same description word for word in every prompt.
  • One idea per shot. MFA, device posture and policy based microsegmentation were cut. Forty eight seconds holds one concept, not a catalogue.
  • Every shot cut to the narration, never looped. An earlier version looped an eight second take under a longer line and replayed its first second before each cut.
  • One shot reshot. The closing door first came back as a concrete basement, which broke the office world the other six shots had built.

Result: a finished piece with the script, the shot list, and the review decisions attached to it, which is the part a reviewer cannot see in the video alone.

AI video / script to screen

Narrated video production pipeline

ElevenLabs TTS RunPod GPU FFmpeg Node.js

A batch pipeline that turns written scripts into finished narrated videos. Scripts come in as structured rows, the narration is synthesised, footage is generated on GPU instances, and text overlays and audio are composed into the final cut.

script → narration (TTS) → generated footage (GPU) → text overlay → audio mix → final video

My part

  • Wrote and structured the scripts, including pacing for narration length
  • Designed the whole pipeline and its 19+ API endpoints
  • Reviewed output for pronunciation of technical terms, pacing, and on screen text
  • Built failover across 3 to 5 GPU instances with error recovery

The AI's part

  • Voiced the narration from my script
  • Generated the footage from prompts I wrote per scene
  • Never decided structure, facts, or final cut

Result: 50+ batch generations a day, with rejected takes most often failing on pacing, filler phrasing, or mispronounced technical terms, which is what the review step exists to catch.

Agents & connected workflows

Multi agent content engine

Claude Gemini OpenRouter React Supabase

Eleven agents that take one proven piece of source content and produce brand specific variations of it. Each agent has its own prompt contract and a structured output schema, with validation between every step and a human review screen before anything is published.

source → analysis → brand adaptation → variation axes → asset generation → human review → export

My part

  • Designed the agent architecture and the shared base class
  • Wrote every prompt contract and output schema
  • Stored prompts in the database with versions, so the content team could adjust tone without a deploy
  • Built the review interface that kept a person in the loop

The AI's part

  • Analysed source material and proposed what could safely vary
  • Drafted copy and generated imagery within those constraints
  • Never performed the combination maths, which is deterministic code

Result: 50+ publish ready pieces per day per brand. First versions were too generic; the fix was constraining what the model was allowed to change rather than asking for more creativity.

The output here is image based social content, not video. It is in this portfolio for the agent design and the prompt versioning, which is the part that transfers.

RAG / grounding

Retrieval grounded writing across 202 sites

FAISS Python pgvector

A retrieval stack over a curated knowledge base, so generated articles are written from the source material instead of from whatever the model remembers. Retrieval runs before generation, the retrieved passages go into the prompt, and the draft is checked back against them.

query → retrieve passages → ground the prompt → draft → check draft against source

My part

  • Built the ingestion, chunking, and embedding stack
  • Wrote the prompt layer that forces the draft to use retrieved passages
  • Added verification after publication, which caught a pipeline silently reporting success while writing nothing

The AI's part

  • Drafted articles from the passages supplied to it
  • Had no authority over whether a draft shipped

Result: a 12 stage pipeline running across a 202 site network, with audits covering roughly 22,000 published pieces.

Prompt engineering & QA

Treating prompts like code

Anthropic API GitLab CI Playwright

Changing a prompt without a test set is guesswork: you fix one case and quietly break another. I keep a set of cases with expected outcomes, including every failure seen in production, and run it before any prompt change ships.

What I put in a prompt

  • Who the audience is and what they should be able to do afterwards
  • Which source material to use, and the instruction to use nothing else
  • Format, length, and tone, with an example of the output I want
  • What to avoid, written from the mistakes the earlier version made

How I check it

  • Schema validation on every output, with a retry on malformed results
  • Regression gates in CI that block a release on quality failures
  • Per finding fingerprinting, so noise rates are measurable over time instead of anecdotal
  • Verification after every automated action, because a success response is not proof

Also: AI generated summaries of technical scan results, turning raw findings into reports a non specialist can act on.
